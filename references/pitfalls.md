# Desktop-control pitfalls and recovery

Read the matching section when a click/type/capture result is unexpected, before coordinate work on scaled or multi-monitor screens, or on credential/settings pages. The entry `SKILL.md` keeps the hard rules.

## Forms, dropdowns and dialogs
- Settings forms with toggles (e.g. Developer Portal Bot page): flipping a toggle is not applied until you press the bottom bar's green save button, which only appears after an edit. Click it, then re-capture until the unsaved bar is gone and the success banner shows. Re-check every toggle you did not mean to touch before saving, since accidental flips happen during scrolling.
- Dropdowns near the bottom edge: scroll the page so the whole menu sits inside the viewport before clicking the trigger; a menu clipped at the window edge hides its longest options. Confirm the selected value (checkmark or field text) in a fresh capture before moving on. `shot` refuses to overwrite an existing file (`File exists`) — always use a fresh filename for each capture.
- Modal dialogs: `Escape` closes the whole modal, not just an autocomplete popup. To dismiss an autocomplete list that overlays a field, click a neutral spot inside the dialog instead. Re-capture after every checkbox toggle, since a click can flip an option you meant to keep; confirm the state before pressing the confirm button. For dark-mode UIs when using `tesseract -l tha+eng`, invert the cropped image first (`ImageOps.invert`) for cleaner OCR; use `tesseract <shot> stdout tsv` to get word bounding boxes when locating text targets by coordinate, and `PIL.ImageChops.difference(before, after).getbbox()` to verify subtle UI changes. Coordinates are pixels of the latest stream screenshot; capture both streams before a cross-monitor drag.

## Coordinates, frames and cursor
- Coordinate calibration: the screenshot pixel size can differ from the portal's logical size under display scaling (for example 125%). Do not apply a guessed scale factor to coordinates. Before relying on a factor, move the pointer to two known UI targets and confirm the landing position in a fresh capture; keep the factor at 1.0 unless that test proves a mismatch. Applying an untested factor made clicks miss.
- Vision-tool downscale: the vision analyzer shows a 1920x1080 capture as 960x540 and reports coordinates in that scale. Multiply vision-read coordinates by 2 before passing them to click/move, and read targets from the full-resolution file, not the thumbnail.
- Missing cursor / frozen frames: GNOME ScreenCast emits a new frame only when the content changes, and the pointer is not drawn unless the stream asks for embedded cursor (`cursor_mode` embedded, value 2, in the ScreenCast options). If captures show no pointer or stop updating after moves, fix the bridge's stream options before retrying clicks; clicks blind on a frozen stream are wasted.
- Locating the pointer: when the cursor is not visible in a capture, make two captures separated by a 2 px relative move (`rel` dx=2 dy=0) and take the `ImageChops.difference` bbox of the pair; the diff region is the cursor, so its top-left plus a few px is the current tip. Use that to compute the `rel` offset to a target, then verify with a fresh capture before pressing.
- Stale-frame check: after each state-changing click, compare `md5sum` of the new capture with the previous one. An identical hash means the frame did not change (click missed, page still loading, or stalled stream); wait and recapture before the next click instead of assuming success.
- Bridge `ok` is not success: the `pc` client prints `ok` when the event is sent, even when the pointer never reaches the window. Only a changed fresh capture confirms a click. After two clicks with an unchanged frame, stop and report the blocked state to the user; do not keep sending clicks into a personal browser.
- Vision read can come back empty: if the vision tool returns no description for a capture, say the screen could not be read. Never describe tabs, text or positions from memory of an earlier capture, and never report a window's content you did not verify in the current frame.

## Small IDs and the alternate bridge
- Reading small on-screen IDs (URL bar, status bar, app IDs): vision reads of a downscaled full-screen capture are unreliable for digits. Hover the link to show its target in Chrome's bottom-left status bar, capture, and read a crop of that strip at full resolution; never report digits from a downscaled view. Alternate bridge (`hermes-portal` user service, `pc` client): when an absolute `click` does not register inside a Chrome page, use relative moves: `rel` by a large negative offset to clamp the pointer to the top-left corner, then `rel` by the target offset, then `press`. Verify with a fresh screenshot before the next action. Full command list is in [controller protocol](controller-protocol.md#portal-bridge-hermes-portal).

## Stale files and stalled streams
- Stale-file trap: a capture command that fails (`no frame`, error, or `File exists`) leaves any previous file at that path untouched. Never open or describe a path after a failed capture without checking its mtime is newer than the attempt; use a new filename each time. Stall recovery: if `quickshot.py` or `shot` returns `no frame` repeatedly, the portal bridge process has stalled. Check the bridge process, restart it, and re-approve the consent prompt before retrying. A persistent user service (`hermes-portal`, with a saved portal token) that reports active/READY removes the repeated consent prompt; confirm it is active with `systemctl --user status` before concluding the stream is down. Do not keep clicking blind while frames are missing. Use private captures and remove unneeded ones. If an action still shows a spinner or unchanged page, wait briefly and capture again before retrying a state-changing click; asynchronous navigation can otherwise create duplicates.

## Credential pages
- Token-reveal pitfall: after Reset/Generate, the token is painted on screen, so every later capture or vision read puts it into the transcript. Click the visible Copy control by coordinates from the last capture taken before the reset (or the layout you already measured), do not capture the token row again, then read the clipboard directly with `wl-paste -n`. Delete any capture that was taken while the token was visible (`rm` the file) and do not open it again.
- Worked Discord example (bot token into a profile `.env`): `wl-paste -n` → `GET https://discord.com/api/v10/users/@me` with `Authorization: Bot <token>` to confirm the identity → write the token to the profile `.env` with `chmod 600` → `wl-copy --clear`. Full bot-app setup flow: [Discord Developer Portal](discord-developer-portal.md).
