# Debian desktop control

Use a dedicated app connector first when it covers the task. Run only the requested desktop actions.

## Screenshot only ("แคป")
1. Run `/usr/bin/python3 -I "$HOME/.claude/skills/debian-desktop-control/scripts/quickshot.py" /absolute/private/out.png`. If it fails with `portal denied or timed out` (no GNOME dialog appears), fall back to `dctl.sh start`, `dctl.sh send "shot @s /absolute/private/out.png"`, then `dctl.sh stop` instead of asking the user to click a missing prompt.
2. Open the PNG. Stop: do not press keys, click, launch apps or start input control.

## Verification handoff
When a CAPTCHA (e.g. hCaptcha on creating a Developer Portal app) appears, stop clicking that page entirely and hand it to the user. Repeated Create clicks while a captcha is pending can produce duplicate app entries; re-check the app list before any retry. When CAPTCHA, password, or MFA appears, notify the user briefly and run `dctl.sh send "wait 10" "shot @s /absolute/private/fresh.png"` in the foreground so they can complete it without another chat round-trip. Inspect the same open tab afterward; continue automatically when verification is gone, including when the page has navigated to the result. Never click or fill authentication secrets/CAPTCHA yourself. If still blocked, stop control and ask only for the remaining verification. When the user says they completed verification, inspect the current screen first and focus the existing browser window only if necessary; do not blindly toggle `alt+Tab` or repeat the submit/reset action, because either can leave the verified page or regenerate a credential.

## Input actions
0. Before any click, type or key press on the desktop, get explicit approval through the host's approval/question card (Hermes `clarify`, Claude Code `AskUserQuestion`) for each new page or flow you are about to operate; approval for one flow does not carry to the next page of the same site. A chat-only question does not count. If the user answers by doing a step themselves (e.g. 'กดเอง'), stop clicking and hand the step back; do not click on their behalf in the same flow. An instruction like 'ทำให้เสร็จ' / 'ทำต่อเลย' given mid-task is not that approval: if the task needs desktop input and no card was answered yes, ask the card first, then act. GNOME portal consent is a separate, earlier grant and does not replace the card. Stop immediately when the user says 'หยุด'.
1. Confirm which browser is on screen before acting. A browser-automation tab (the agent's own browser) is invisible to the user, so a page opened there is not 'opened for the user'. To act in the user's own Chrome window, drive it through this desktop control and check it with a fresh capture. Use a fresh screenshot to identify the target. Run only one controller. If GNOME asks for consent, let the user grant it; never enter passwords/OTPs or bypass CAPTCHA. After handing off to the user for CAPTCHA, MFA, or login in a browser, resume on that **existing open tab** (e.g. `key alt+Tab` or focus the window) — never re-open the URL with `xdg-open`, which creates a new tab/session and re-triggers verification.
2. Start: `bash "$HOME/.claude/skills/debian-desktop-control/scripts/dctl.sh" start` (automatically shows the top-center click-through red-dot indicator via `scripts/indicator.py` until `stop`). Keep that visible indicator whenever controlling the desktop; it is the user's requested signal that control is active. If `start` fails with `not ready (GNOME may be waiting for consent)`, inspect `${XDG_RUNTIME_DIR:-/tmp}/dctl/out.log` and `journalctl --user -u xdg-desktop-portal* -n 20` to distinguish a waiting prompt from `Only the focused app is allowed to show a system access dialog` (portal refuses to show consent from an unfocused/background shell when `restore-token` is rejected). When the user is ready to approve a consent dialog, start the same command with your host’s background execution support. In Codex, use `exec_command` with `yield_time_ms: 1000`, notify the user to click **Share / Allow**, then poll the returned session with `write_stdin` until the command exits 0 and reports `ready`.
3. Send known steps in one `send` call, e.g. `bash "$HOME/.claude/skills/debian-desktop-control/scripts/dctl.sh" send "click @s 100 200" "wait 0.3" "shot @s /absolute/private/check.png"`. Always include `@s X Y` on `move` and `click` (bare `click` after `move` fails). Replace example coordinates from the current screenshot. Do not batch past a result you must inspect first. Commands stop on the first error; no extra shell sleep is needed.
   Scrolling: the wheel scrolls the pane under the pointer, so `move @s` onto the page content (not the sidebar or an open dropdown) before `scroll`; otherwise the wrong pane moves or nothing does.
4. Use `speed fast` (smooth default), `human` or `slow`. Never use `jump` or `speed instant`. Prefer shortcuts when useful; `Super_L+v` opens the clock panel on this machine. `@s` is filled in except inside typed text.
5. Use `type "text"` (double quotes) for Thai/mixed text, or `wl-copy` + `key ctrl+a` + `key shift+Insert` to reliably replace existing field text. Inspect the pasted text before Enter/Save. In web dialogs, `type` into a freshly opened input can silently fail: click the field first, then paste (`printf 'text' | wl-copy` → `click @s X Y` → `key ctrl+v`) and confirm the field in a fresh capture. Clear the clipboard (`wl-copy --clear`) afterward.
6. Open the final capture, verify the result, then run the same script with `stop`.
7. Verify every state-changing action with a **fresh, newer** capture: a bridge `ok`, an exit code or an unchanged frame (same `md5sum`) is not success. After two clicks with an unchanged frame, stop and report the blocked state. Never describe a screen you did not read in the current frame, and never open a path after a failed capture (`no frame`, `File exists`) without checking its mtime. Use a new filename for each private capture and remove unneeded ones. If a page still shows a spinner or is unchanged, wait and recapture before retrying a state-changing click; asynchronous navigation can otherwise create duplicates.
8. Do not apply an untested display-scale factor to coordinates. Read small digits/IDs from a full-resolution crop, never from a downscaled view. For calibration, cursor location, frozen streams, stalled bridges, forms/dropdowns/modals and the alternate `hermes-portal` bridge, read [pitfalls](references/pitfalls.md).

## Credential-bearing pages
For authorized application/bot tokens, use the visible Copy control and read the clipboard directly into a private local credential file; never echo clipboard contents, token prefixes, or token-bearing OCR into tool output. After Reset/Generate, do not capture the token row again and delete any capture taken while it was visible; details and a worked example are in [pitfalls](references/pitfalls.md#credential-pages). Validate the copied value before saving it and verify it with the provider's bot/application identity endpoint; a successful clipboard command can still return stale text. Set restrictive file permissions and clear the clipboard afterward. Treat token screenshots as sensitive and avoid broad OCR on them. Passwords, OTPs, and CAPTCHA remain user-only under the verification handoff above.

Security-relevant options on these pages (token expiry, scope, repository access, permissions) are the user's choice: a page default or an option that weakens security (such as no expiration) needs an explicit answer from the user through the approval card before you select it. Read the confirmation dialog text before pressing its confirm button, since it often states the consequence (e.g. 'will never expire').

For other commands or manual fallback, read [controller protocol](references/controller-protocol.md). Report missing session/portal consent or failed actions; do not claim control succeeded from a process exit alone.
